## 1. 작업 시작 전 — 컨텍스트 파악 (필수)

코드를 수정하기 **전에**, 관련 구조·규칙·문맥을 먼저 이해하고 시작한다.
특히 **다른 세션이 하던 작업을 이어받을 때** 반드시 수행한다.

- **문서 먼저 읽기**: `README`, 이 `AGENTS.md`, `docs/`, 관련 설정 파일.
- **구조 파악**: 수정할 영역의 디렉토리 구조와 관련 파일 흐름을 훑는다. 전체를 다 읽을 필요는 없고, **건드릴 부분과 그 주변**을 이해한다.
- **기존 규칙 따르기**: 이미 쓰이는 패턴·네이밍·유틸을 재사용한다. 새로 만들기 전에 비슷한 게 있는지 먼저 찾는다.
- **이어받기 체크**(다른 세션/작업 인계 시):
  - 최근 커밋·브랜치 상태 확인 (`git log`, `git status`, 진행 중 브랜치).
  - 미완성 작업·TODO·주석·임시 파일 확인.
  - 무엇이 끝났고 무엇이 남았는지 **먼저 정리해 공유**한 뒤 착수한다.
- 파악한 내용과 이해가 실제와 다르면, 진행 전에 **차이를 먼저 알린다**.

## 2. 문서 관리 루틴 — 핵심 문서 3종

> 목적: 컨텍스트 압축·다른 세션 이어받기에 대비해 작업 맥락을 문서로 남긴다.

작업 시작 시 세 파일이 있는지 **확인**한다. 없으면 만들고, 있으면 읽고 현황을 파악한 뒤 착수한다.

- `README.md` → **저장소 루트**
- `docs/PLAN.md`, `docs/WORKLOG.md` → **`docs/` 폴더** (없으면 폴더도 함께 생성)

### 📄 README.md — 프로젝트 개요 (루트)

- 루트에 **없으면 생성**하고, 저장소 내용을 파악해 그에 맞게 작성한다.
- **작업 단위가 끝날 때마다** 변경된 내용(구조·기능·실행법 등)을 반영해 갱신한다.

### 📋 docs/PLAN.md — 계획 · 진행 체크리스트

- **없으면 생성**(`docs/` 폴더 포함)하고, **있으면 먼저 읽어 현재 계획을 파악**한다.
- 계획이 수립되면 **PLAN.md에 먼저 기록한 뒤** 작업을 시작한다.
- **체크박스(`- [ ]` / `- [x]`)로 작성**하고, 작업을 진행하면서 완료 항목을 **체크해 나간다**.
- 계획이 바뀌면 즉시 **갱신**한다(항목 추가·수정·삭제 반영).

### 📝 docs/WORKLOG.md — 작업 기록

- **없다면 먼저 CHANGELOG.md 가 있는지 체크하고 없으면 생성**(`docs/` 폴더 포함)하고, **있으면 먼저 읽어 이전 맥락을 파악**한다.
- **작업 단위가 끝날 때마다 기록**한다.
- **다른 세션·다른 사람이 읽고 바로 이어받을 수 있도록** 구체적이고 디테일하게 적는다:
  - 무엇을 / 왜 했는지, 건드린 파일, 주요 결정과 이유, 남은 일·주의점.
- 이어받는 세션은 시작 시 WORKLOG를 읽어 이전 맥락을 따라잡는다.

### 작업 완료 후 — 세 파일 정리 (마무리 루틴)

작업 단위를 끝낸 뒤에는 **README · docs/PLAN · docs/WORKLOG 세 파일을 한 번에 훑어 정리**한다.

- `README.md`: 바뀐 내용이 반영됐는지 확인, 누락 보완.
- `docs/PLAN.md`: 완료 항목 체크 상태 최신화, 새로 생긴 할 일 추가.
- `docs/WORKLOG.md`: 이번 작업에서 못 적은 내용이 있으면 채워 넣는다.

→ 이 정리를 마쳐야 "작업 단위 완료"로 본다.

### 요약 흐름

```
[시작]  세 파일 확인 → 없으면 생성 / 있으면 읽고 파악
        README.md(루트) · docs/PLAN.md · docs/WORKLOG.md
   │
[작업]  docs/PLAN에 계획 기록 → 작업하며 체크박스 갱신
   │
[완료]  README·docs/WORKLOG 기록 → 세 파일 싹 정리(누락 보완)
```

## 3. 보안 · 비밀정보 (최우선, 예외 없음)

- `.env`, `*.key`, `*.pem`, `credentials`, `secrets/` 등 **비밀파일은 읽기·출력·커밋·푸시 금지**.
  - 내용을 채팅/로그/PR 설명에 **표시하지 않는다**.
- API 키·토큰·비밀번호를 코드에 **하드코딩 금지** → 반드시 환경변수·시크릿 매니저 참조.
- 로그·에러 메시지·주석에 민감정보(키, 개인정보) 노출 금지.
- 새 비밀파일을 만들면 즉시 `.gitignore`에 패턴이 있는지 확인한다.
- 외부 서비스로 코드·데이터를 전송하는 작업(업로드, 배포, 웹훅)은 **사전 승인** 후 진행.

## 4. Git · 배포 · 파괴적 작업

- **커밋·푸시·PR·병합은 명시적 요청/승인 후에만** 진행한다. 자동으로 하지 않는다.
- `main` / `master`에 **직접 커밋 금지** → 항상 작업 브랜치를 만든다.
- **되돌리기 어렵거나 데이터를 잃을 수 있는 작업은 실행 전 반드시 승인**받는다:
  - Git: `git push --force`, `git reset --hard`, `git clean`, 브랜치/태그 삭제.
  - 파일: `rm -rf`, 대량 삭제, 기존 파일 덮어쓰기(내가 만들지 않은 파일).
  - 데이터: DB `DROP`/`DELETE`/`TRUNCATE`, 마이그레이션 rollback, 프로덕션 데이터 조작.
  - 실행 전에 **무엇을 지우는지·왜 필요한지** 한 줄로 설명하고 확인을 받는다.
- 삭제/덮어쓰기 전에는 대상을 **먼저 확인**한다. 설명과 실제 내용이 다르거나 내가 만든 게 아니면, 진행하지 말고 알린다.
- 커밋 메시지 규칙:
  - 형식: (예) Conventional Commits — `feat:`, `fix:`, `docs:`, `refactor:` …
  - 언어: **한글** (또는 프로젝트 합의)
- PR 설명에는 **무엇을·왜** 바꿨는지 요약한다.

## 5. 작업 범위 · 소통

- **요청한 범위만** 수정한다. 시키지 않은 대량 리팩터링·파일 정리 **금지**(스코프 크리프 방지).
- 요구사항이 애매하면 **추측하지 말고 질문**한다.
- 큰 변경(구조 변경, 여러 파일 수정) 전에는 **계획을 먼저 공유**하고 동의를 받는다.
- 선택지 제안 및 방향 제안 시 트레이드오프에 대해 가감없이 명시한다.
- 작업 결과는 **정직하게** 보고한다: 테스트가 실패하면 실패했다고, 건너뛴 단계가 있으면 건너뛰었다고 말한다.
- 응답은 반말로 하지 않는다.
- 응답·문서 언어: **한글**.

**에러 · 실패 시 행동**

- 같은 문제로 **2~3회 시도해도 안 되면 멈추고**, 무엇을 시도했고 왜 막혔는지 정리해 **사람에게 묻는다**. 같은 방식 무한 반복 금지.
- 실패를 **숨기거나 우회로 덮지 않는다**. 에러 메시지·원인을 그대로 공유한다.
- 원인이 불확실하면 **추측으로 대충 고치지 말고**, 먼저 진단(로그·재현)한 뒤 대응한다.
- 시도한 변경이 문제를 악화시키면 **되돌리고(원상복구)** 상황을 알린다.
